# 第4章时间过程诊断与候选节点机制审查

日期：2026-05-05

## 1. 本文当前任务到底是什么

当前第4章不是一个普通的静态节点分类任务，也不是严格意义上的 128 个全网节点自由定位任务。当前实际任务应定义为：

> 在保留 128 节点全网拓扑的条件下，仅使用固定监测布局 degree N25 的稀疏动态观测，对持续性 I/E 缺陷进行过程活跃期判断，并在 50 个候选缺陷节点中进行排序定位。

这个任务包含三个空间集合和一个时间过程：

| 符号 | 含义 | 当前规模 | 作用 |
|---|---|---:|---|
| V | 全网图节点集合 | 128 | 图结构输入与空间传播约束 |
| S | 监测节点集合 | 25 | 动态观测输入来源 |
| C | 候选缺陷节点集合 | 50 | 缺陷注入与正式定位输出空间 |
| D | 实际激活缺陷节点集合 | 50 | 正式 IE420 矩阵中的真实缺陷节点 |

三者不能混写：

- V 是模型看到的拓扑范围。
- S 是模型能看到动态时序值的节点范围。
- C 是模型正式被要求排序定位的缺陷假设空间。

当前代码和数据的实际状态为：

- `node_list.json` 包含 128 个节点。
- `adj_matrix.npy` 为 `128 x 128`。
- `graph_path_features.npz` 中 `shortest_dist`、`pipe_length_dist`、`flow_direction`、`elevation_diff` 均为 `128 x 128`。
- `candidate_nodes_new.json` 包含 50 个候选缺陷节点。
- `monitor_nodes_degree_N25.json` 包含 25 个监测节点。
- 监测节点与候选缺陷节点交集为 12。
- 正式母数据中每个场景有 `128 x 287 = 36736` 条节点-时间记录，说明当前母数据是全图时序数据，不是 monitor-only 子图。

模型实现层面：

- 模型对 128 个节点产生节点分数 `logits_node`。
- 训练和评价时使用 `candidate_mask` 将正式定位损失与 Top-K 评价限制在 50 个候选缺陷节点内。
- 使用 `observed_mask` 表示哪些节点有动态观测输入。

因此，第4章不能写成“128 节点全网自由定位”，更准确的说法是“全图拓扑约束下的候选缺陷节点排序定位”。

## 2. A 线：时间过程诊断主线

### 2.1 当前状态

当前时间主线由五个层次组成：

1. 时间门控缺陷注入。
2. 窗口级时间标签。
3. 时间位置编码。
4. 时间派生特征。
5. 过程级评价指标。

正式缺陷矩阵包含 `start_hour` 和 `duration_h`。这意味着一个缺陷场景不是从头到尾全程注入，而是在指定起始时间和持续时长内激活。

数据窗口构造时，每个窗口会计算其时间范围与真实缺陷激活区间的重叠比例 `overlap_ratio`。当前 time-gated 口径可理解为：

| 窗口状态 | 判定依据 | 作用 |
|---|---|---|
| inactive | 与缺陷激活区间无重叠 | 不参与定位 |
| transition | 有重叠但不足 active 阈值 | 反映边界过程 |
| active | 重叠比例达到 active 阈值 | 参与活跃期检测与定位 |

当前正式 baseline 并不是只有静态定位，而是：

```text
time-gated 注入
+ time-gated 窗口标签
+ sin(hour), cos(hour) 时间位置编码
+ observed_mask
+ residual8
+ active detection
+ candidate localization
+ event-level evaluation
```

### 2.2 时间编码的作用

时间编码不是可有可无的装饰。窗口样本在训练中以 batch 形式随机输入，模型不能依靠 batch 顺序知道一个窗口在原始场景时间轴中的位置。因此，时间编码承担了向模型显式提供窗口时间位置的作用。

当前实现中的 `sin(hour), cos(hour)` 表达的是日内时刻。如果所有场景从统一仿真起点开始，它可以近似表示场景内时间位置。但从任务定义上看，它仍然更像“日内周期编码”，还不是最严格的“场景相对时间编码”。

因此，当前时间编码机制是合理的，但仍可补强：

```text
当前：sin(hour), cos(hour)
建议补充：relative_time = time_since_scenario_start / total_scenario_time
```

更完整的时间输入应为：

```text
日内时间编码 + 场景相对时间编码
```

### 2.3 always_on 的含义与当前结论

`always_on` 不是重新生成了一套全程注入数据，而是在同一套 time-gated 数据上改变窗口标签解释方式。由于底层仿真仍然只在 `start_hour + duration_h` 对应时段注入缺陷，因此这种设置不能被解释为“全程注入实验”。

更严格地说，当前 `always_on` 只是一个标签协议对照或错误边界检查：它检验如果不使用真实注入时段来监督窗口标签，而是把缺陷场景更粗地标成“有目标/需诊断”，指标会发生什么变化。它不具备物理注入口径上的合理性，不能作为正式任务设定。

`time_gated` 使用真实注入时段定义窗口是否 active。`always_on` 则改变标签解释而不改变底层仿真数据，这会让活跃期检测任务变得不真实：模型可能在非注入时段也被要求寻找缺陷目标。因此 `active_period_recall` 变高并不代表过程诊断能力增强，只能说明该标签协议降低或扭曲了检测任务。

当前结果中：

| 设置 | MRR | Top-1 | Active Recall | Detection Latency | Event Top-1 |
|---|---:|---:|---:|---:|---:|
| time_gated baseline | 0.7933 | 0.6721 | 0.9708 | 0.1111 | 0.7302 |
| always_on | 0.3615 | 0.2668 | 1.0000 | 0.0000 | 0.6667 |

这说明 `always_on` 的检测指标表面更好，但窗口级定位明显变差。更准确的解释是：

- `always_on` 让更多非真实活跃期、弱响应、边界响应或低 overlap 窗口参与定位。
- 这些窗口虽然属于同一缺陷场景，但缺陷传播尚未充分发展或已经衰减，空间定位信息更弱。
- 甚至在真实未注入窗口中，标签仍可能要求模型定位某个缺陷节点，这会造成监督信号与物理响应不一致。
- 因此该结果不应解读为 `always_on` 的过程检测能力更强，而应解读为：脱离真实时间门控的标签会破坏全过程定位任务。

因此，当前 `always_on` 不建议进入正文主线。若保留，只能放在附录或方法审查中，用于说明为什么必须采用 time-gated 标签。后续审查重点是：

```text
统计 time_gated 与 always_on 下 active 窗口数
统计 loc_enabled 窗口数
比较参与定位窗口的 overlap_ratio 分布
比较低 overlap / 高 overlap 窗口的定位性能
检查 always_on 是否引入了大量真实非注入期定位样本
```

如果论文需要真正比较“全程注入”和“时间门控注入”，必须重新生成全程注入仿真数据，而不是只修改标签。正确对照应为：

```text
数据 A：time-gated 注入 + time-gated 标签
数据 B：全程注入仿真 + always-active 标签
```

当前已有 `always_on` 结果只能回答“标签不遵循真实注入时间会怎样”，不能回答“全程注入任务表现如何”。

### 2.4 trend 负结果不能直接跳过

当前 `trend` 特征是窗口后半段残差均值减去前半段残差均值，然后将该趋势值重复拼接到窗口每个时间步。

当前结果中：

| 设置 | MRR | Top-1 | Active Recall | Detection Latency | Event Top-1 |
|---|---:|---:|---:|---:|---:|
| time_gated baseline | 0.7933 | 0.6721 | 0.9708 | 0.1111 | 0.7302 |
| time_gated with trend | 0.1032 | 0.0128 | 0.6359 | 1.2909 | 0.0317 |

这个负结果幅度过大，不能简单写成“trend 无效”。需要排查：

- trend 特征尺度是否异常。
- trend 是否与 active 标签错位。
- trend 是否只强调变化边界，而不适合稳定活跃期定位。
- trend 作为窗口级统计量重复到每个时间步，是否破坏时序模型输入分布。
- 水力 trend 与水质 trend 是否表现不同。

后续应做：

```text
trend 特征分布检查：均值、方差、极值、缺失值
trend 与 residual8 的相关性分析
只加水力 trend
只加水质 trend
trend 仅作为统计分析变量，不直接拼接进模型输入
按 inactive / transition / active 分组比较 trend 分布
```

若审查后仍然负面，可在论文中写成：

> 简单窗口差分趋势并未改善定位，说明当前缺陷定位更依赖完整时序残差形态与图传播结构，而非粗粒度前后差分统计。

### 2.5 时间评价机制与任务定义

时间评价机制必须服务于当前任务定义。当前第4章任务不是“给定一个窗口直接定位节点”这么简单，而是：

> 在连续运行过程中，先判断缺陷活跃期，再在活跃窗口和事件层面定位候选缺陷节点。

因此，正式评价应至少包含三类指标：

| 指标类别 | 指标 | 解释 |
|---|---|---|
| 窗口级定位 | MRR、Top-1、Top-3、Top-5 | active 窗口内真实节点排序 |
| 活跃期检测 | active_period_recall、false active rate | 是否识别缺陷活跃过程 |
| 事件级定位 | event_level_top1/top3/top5、detection_latency_mean | 场景级聚合诊断能力与响应速度 |

当前已有的过程级指标是合理的，但仍需要补充更直接的时间诊断分析：

```text
按 start_hour 分组的 active recall
按 duration_h 分组的 event-level Top-K
transition 窗口误判率
首次检测时间相对真实 start_hour 的偏差
active 预测时间轴可视化
```

### 2.6 A 线当前判断

当前时间主线已经具备基本闭环：

- 数据中有时间门控注入。
- 数据集构造中有 overlap-based 标签。
- 模型输入中有时间位置编码。
- 评价中有 active recall、latency、event-level Top-K。

但它还没有完全达到论文中“时间过程诊断机制充分验证”的程度。最需要补的是：

1. time_pos 多种子复核。
2. 场景相对时间编码实验。
3. always_on 参与定位窗口构成分析。
4. trend 负结果机制排查。
5. 按 start_hour / duration_h 的分组评价。

## 3. B 线：候选节点机制主线

### 3.1 当前状态

当前候选节点机制为：

```text
V = 128 个全网节点，作为图结构空间
C = 50 个候选缺陷节点，作为正式缺陷注入与定位输出空间
S = 25 个监测节点，作为动态观测空间
```

正式 IE420 矩阵中：

- I 类 250 个场景，覆盖 50 个候选节点。
- E 类 170 个场景，覆盖 34 个合法候选节点。
- 总激活缺陷节点为 50。
- 监测节点与激活缺陷节点交集为 12。

这说明 C 不是只用于评价，它也是正式缺陷矩阵和后续第五章布局优化的基础。

### 3.2 合理性

候选节点机制本身可以成立，但必须解释为工程任务假设，而不是为了降低难度随意缩小输出空间。

合理叙事应为：

> 排水管网全网节点并非都具备同等缺陷注入语义、仿真合法性和工程诊断优先级。本文先基于管网结构、可仿真性和工程关注范围定义候选缺陷节点集合 C，并在该候选空间内开展过程诊断与监测布局优化。

当前设定的合理性在于：

- 全图 V 保留空间传播结构。
- 监测集 S 模拟有限传感器观测条件。
- 候选集 C 明确缺陷诊断假设空间。
- 第5章可以固定 C，只优化 S，从而避免同时改变任务与布局。

### 3.3 风险

候选节点机制的主要风险是论文表述越界。

不能写：

```text
本文实现 128 节点全网自由定位。
```

应写：

```text
本文在 128 节点全网拓扑约束下，对 50 个候选缺陷节点进行排序定位。
```

另一个风险是 C 的来源说明不足。如果 C 的构造过程没有讲清楚，读者会认为这是人为降低难度。因此第3章必须补强候选节点选择依据：

```text
候选节点的拓扑覆盖
候选节点的工程语义
候选节点与监测节点关系
候选节点与实际激活缺陷节点关系
哪些候选节点不具备 E 类合法渗漏语义
为什么不是 128 全部节点
```

### 3.4 B 线后续实验设计

候选节点机制后续实验应分清三个变量：

| 实验类型 | 改变的变量 | 回答的问题 |
|---|---|---|
| 输入图大小实验 | V | 为什么输入要保留全图拓扑 |
| 输出空间边界实验 | C | 候选节点约束带来多大影响 |
| 监测布局优化实验 | S | 监测点怎么布置更利于诊断 |

这三个变量不能同时改变。

建议实验 1：输入图大小影响分析。

```text
V = monitor-only 25 节点图
V = candidate-only 50 节点图
V = S ∪ C 图
V = full 128 图
```

该实验回答：

> 为什么第4章采用 full-graph sparse-observation，而不是只用监测节点或候选节点子图？

建议实验 2：输出空间边界分析。

```text
C = 50 正式候选节点
C = 128 全网节点
C = 50 + 非候选 hard negatives
```

该实验回答：

> 当前 50 候选节点任务与全网自由定位任务之间差距多大？

如果 C=128 性能明显下降，说明当前论文应明确限定为候选缺陷空间定位，并将全网自由定位作为后续工作。如果 C=128 仍保持较好结果，则第4章贡献可以升级。

建议实验 3：候选集可解释性分析。

```text
C 到 S 的最短路距离分布
C 中 direct / near / far 分层
I/E 覆盖差异
候选节点拓扑分布图
候选节点与非候选节点的结构差异
```

### 3.5 第5章如何承接

第5章应固定 V 和 C，只改变 S。

推荐表述：

> 在第3章构建的候选缺陷空间 C 和第4章建立的诊断评价器基础上，第5章仅改变监测节点集合 S，研究不同监测布局对候选缺陷定位性能的影响。

这样第五章的变量是清楚的：

```text
固定：V、C、缺陷矩阵、诊断任务、评价器
改变：S，即监测节点集合
```

如果第五章同时改变 C 和 S，就会变成重新定义诊断任务，不利于论文主线闭合。

## 4. 当前设计合理性与实验结果

### 4.1 合理性

当前设计的科学合理性可以概括为：

1. 排水管网缺陷响应具有空间传播性，因此保留全网拓扑 V 是合理的。
2. 工程监测条件有限，因此只在 S 上提供动态观测是合理的。
3. 缺陷注入和定位需要明确假设空间，因此定义候选缺陷节点 C 是合理的。
4. 持续性 I/E 缺陷不是静态事件，因此采用 time-gated 注入、窗口标签和事件级评价是合理的。

### 4.2 已有结果支持

当前正式 scenario split 三种子结果：

| 指标 | 均值 |
|---|---:|
| MRR | 0.7778 |
| Top-1 | 0.6426 |
| Top-3 | 0.9033 |
| Top-5 | 0.9503 |
| Active Period Recall | 0.9590 |
| Event Top-1 | 0.6614 |
| Event Top-3 | 0.9365 |
| Event Top-5 | 0.9735 |

这说明当前主线在候选缺陷空间内具有较强的场景泛化和事件级定位能力。

node_holdout 三种子结果：

| 指标 | 均值 |
|---|---:|
| MRR | 0.2609 |
| Top-1 | 0.0983 |
| Top-3 | 0.3047 |
| Top-5 | 0.4934 |
| Active Period Recall | 0.9122 |
| Event Top-1 | 0.1083 |
| Event Top-3 | 0.3011 |
| Event Top-5 | 0.4969 |

这说明模型在未见缺陷节点上的定位仍然困难，但活跃期检测能力仍保留。该结果应作为泛化边界分析，而不是主性能证明。

时间维度 seed42 结果：

| 设置 | MRR | Top-1 | Active Recall | Event Top-1 |
|---|---:|---:|---:|---:|
| time_gated baseline | 0.7933 | 0.6721 | 0.9708 | 0.7302 |
| no time_pos | 0.8088 | 0.7071 | 0.9790 | 0.7143 |
| trend | 0.1032 | 0.0128 | 0.6359 | 0.0317 |
| always_on | 0.3615 | 0.2668 | 1.0000 | 0.6667 |

这些结果说明：

- time-gated baseline 是当前最合理的正式过程诊断口径。
- 当前 always_on 只是标签协议对照或错误边界检查，不能替代 time-gated 主线，也不能解释为全程注入实验。
- trend 是强负结果，需要机制排查。
- time_pos 是否稳定贡献，需要多种子复核，不能凭单 seed 改主线。

## 6. 整个故事应该怎么讲

建议论文主线讲成：

> 排水管网缺陷诊断面临两个核心困难：一是有限监测条件下如何利用全网拓扑进行空间定位；二是持续性缺陷并非静态事件，必须在连续运行过程中识别其活跃期并完成定位。为此，本文首先构建覆盖 128 节点全网拓扑的 SWMM 仿真数据，并定义 50 个候选缺陷节点作为工程诊断假设空间。在第4章中，本文固定 degree N25 监测布局，保留全网拓扑但仅暴露监测节点动态观测，建立 full-graph sparse-observation 诊断模型，实现 time-gated 过程活跃期检测与候选缺陷节点排序定位。在第5章中，本文固定第3章数据与第4章诊断评价器，仅改变监测节点集合，研究监测布局对候选缺陷定位能力的影响。

这个故事里，第3、4、5章的关系是：

```text
第3章：定义数据、V/C/S 集合、IE420 时间门控缺陷场景。
第4章：固定 S，研究诊断模型能否在 C 内完成过程定位。
第5章：固定 V 和 C，优化 S，研究监测布局影响。
```

科学合理性解释为：

1. 使用全图 V 是因为缺陷响应沿管网传播，不能裁掉未监测节点拓扑。
2. 使用监测集 S 是因为工程上不可能全网实时观测。
3. 使用候选集 C 是因为正式缺陷注入和定位需要工程可解释、仿真合法的假设空间。
4. 使用 time-gated 是因为持续性缺陷具有发生时间和持续时间，不能退化成静态标签。
5. 使用事件级指标是因为真实诊断关心的是一个缺陷事件最终能否被定位，而不仅是单个窗口是否命中。

需要严格避免的表述：

```text
本文完成 128 节点全网自由定位。
本文已经解决未见节点泛化。
always_on 优于 time_gated。
always_on 表示全程注入实验。
trend 负结果无需解释。
time_pos 单 seed 结果足以决定是否保留时间编码。
```

更稳的表述：

```text
本文完成全图拓扑约束下的候选缺陷节点全过程诊断。
本文在 scenario split 下验证了模型的场景泛化能力。
node_holdout 揭示了未见缺陷节点定位仍是边界问题。
time-gated 口径更符合持续性缺陷过程诊断任务。
当前 always_on 结果说明脱离真实注入时间的标签协议会扭曲过程定位任务；真正的全程注入对照需要重新生成全程注入数据。
候选空间和全网自由定位之间的差异需通过边界实验进一步量化。
```
